# Sergey Embedding Sidecar Plan

## Goal

Build the ultimate Sergey enrichment sidecar: a point-in-time, evidence-backed fighter intelligence layer that combines quantitative fight stats, ELO, opponent quality, contextual annotations, and similarity retrieval.

The end state is not "LLM makes betting picks." The end state is:

```text
core model probability
+ market price
+ fighter trait evidence
+ matchup similarity evidence
+ contextual risk/upside flags
= bet / skip / upgrade / downgrade decision support
```

The system should help answer hard questions like:

```text
When is a 51% model edge actually worth betting?
When is a 65% favorite fragile and worth skipping?
When does a low-confidence underdog deserve an upgrade?
When does the model miss a style problem that stats can reveal?
```

Think of this as "statistical tape review": extracting the same kinds of conclusions a human would get from watching tape, but using point-in-time historical measurements and transparent evidence.

## North-star workflow — evidence packet + LLM context judge

The long-term product should move from rigid threshold betting:

```text
if pick_prob >= 65%:
    eligible
else:
    skip
```

to a context-aware review flow:

```text
Fight A vs Fight B
  -> core model prediction
  -> market edge and odds bucket
  -> pre-fight ELO and opponent-quality context
  -> trait deltas: cardio, durability, control, anti-control, pressure, variance
  -> similar fighter retrieval
  -> similar historical matchup retrieval
  -> backtested ROI/hit-rate for matching patterns
  -> structured evidence packet
  -> LLM evidence review
  -> context score 1-10
  -> final action: bet / lean / skip / downgrade / human review
```

The LLM should not invent a new probability or act as the betting model. It should behave like a disciplined tape-review analyst that can only reason over a grounded evidence packet. The evidence packet is generated by deterministic tools and database queries; the LLM only summarizes, weighs, and explains whether the context supports an upgrade or downgrade.

Example target output:

```text
Base model: 61%
Market edge: +6%
Current rule: skipped by favorite confidence threshold
ELO: +140 for model pick
Similar historical pattern: 18-6, +22% ROI
Trait matchup: cardio/control advantage
Risk flags: low UFC sample, expensive line

LLM context rating: 8/10
Decision: upgrade from skip to eligible 1x bet
Reason: the thin model probability is supported by repeatable, backtested context.
```

Nearest individual examples are illustrative only. They should help an analyst sanity-check the context, but they should not create upgrade/downgrade flags by themselves because nearest-neighbor samples are often small. Decision support should come from aggregate pattern stats with meaningful sample sizes.

This is the safer version of "remove rigid bands." Do not remove the bands blindly. Instead, add audited upgrade paths:

```text
base confidence >= 60%
AND model edge positive
AND deterministic context supports the pick
AND LLM context score >= 8/10
=> eligible small bet
```

or:

```text
base confidence >= 65%
BUT context score <= 4/10
AND risk flags include fragile favorite / bad anti-control / similar negative outcomes
=> downgrade to skip or require a better price
```

The sidecar should eventually store these evidence packets and context reviews so every decision can be audited, backtested, and improved.

## Core principles

1. **Do not replace the core model first.** Keep `mar_4_v2` stable while the sidecar proves value.
2. **Everything must be point-in-time.** A fighter trait at `as_of_date` can only use fights before that date.
3. **Qualitative labels must be evidence-backed.** Do not call someone "bad cardio" unless late-round metrics support it.
4. **Embeddings are for retrieval, not blind authority.** Similarity must return explainable trait deltas and historical examples.
5. **Separate stable traits from matchup context.** Fighter ability, opponent-specific problems, and event-specific notes are different layers.
6. **Every decision adjustment needs an audit trail.** If a 51% bet is upgraded, the system must say exactly why.

## Evidence-only posture for the independent pipeline

The current sidecar work is an empirical context-packet pipeline, not a betting decision engine.

The packet should provide:

```text
measured pattern stats
point-in-time fighter/opponent context
market/model/ELO comparisons
recent-fight evidence
support/risk flags
missing-data flags
links back to source rows
```

The packet should avoid prematurely deciding:

```text
bet this
skip this
upgrade this
downgrade this
stake this amount
```

Downstream, an agent may receive the context report plus sidecar database access and derive its own conclusion. Therefore, new work should add transparent evidence and queryable details rather than hard constraints that prevent the agent from reasoning over edge cases.

`pattern_score_v0` is an empirical evidence score only. Its labels should be interpreted as evidence strength, not final actions:

```text
strong_empirical_support
moderate_empirical_support
neutral_empirical_context
negative_empirical_signal
```

## Phase 0 — `pre_sergey` ELO-only mathematical analysis

### Why this phase exists

The broader plan already covers ELO in Phase 2, but ELO deserves a separate first milestone before traits, embeddings, retrieval, or LLM summaries.

This phase asks:

```text
How much betting signal can we extract from Sergey ELO alone?
```

Do this before vector embeddings because ELO is simple, interpretable, and mathematically testable. If ELO alone explains useful bet/skip patterns, those findings become the baseline that embeddings must beat.

### Objective

Build a standalone ELO backtest analysis layer that joins Sergey pre-fight ELO snapshots to existing backtest results and measures whether ELO can improve bet/skip decisions.

### Work

1. Use the sidecar `fights` table to map pre-fight ELO onto backtest rows.
2. Join by:
   - fight date
   - unordered fighter pair
   - optional mapped fight ID once Phase 1 exists

### ELO-only tests to run

#### 1. Raw ELO validity

Question:

```text
Do higher-ELO fighters actually win more often?
```

Tests:

- win rate by ELO difference bucket
- calibration of ELO implied probability
- Brier/log loss of ELO-only implied probability
- ELO favorite win rate by odds bucket

Example buckets:

```text
pick_elo_diff <= -200
-200 to -100
-100 to -50
-50 to +50
+50 to +100
+100 to +200
>= +200
```

#### 2. Model and ELO agreement

Question:

```text
Are model picks better when the model agrees with ELO?
```

Tests:

- model pick ROI when `model_agrees_with_elo = true`
- model pick ROI when `model_agrees_with_elo = false`
- confidence buckets split by ELO agreement
- edge buckets split by ELO agreement

What we are looking for:

- thin model edges that become safer with ELO agreement
- high-confidence picks that become dangerous with ELO disagreement

#### 3. The 51-60% zone

Question:

```text
Can ELO tell us when a low-confidence pick is a bettable 51-60%?
```

Tests:

- ROI for 51-55% picks with positive ELO diff
- ROI for 51-55% picks with negative ELO diff
- ROI for 55-60% picks with positive ELO diff
- ROI for 55-60% picks with negative ELO diff
- minimum ELO delta that makes thin edges profitable

What we are looking for:

- upgrade rules like:

```text
base confidence >= 51%
AND edge > threshold
AND pick_elo_diff >= +100
=> eligible small bet
```

#### 4. Favorite fragility

Question:

```text
Can ELO identify favorites that should be skipped?
```

Tests:

- favorites with negative ELO diff
- favorites with small ELO diff
- favorites where market implies dominance but ELO does not
- model favorites above 60% where ELO disagrees

What we are looking for:

- downgrade rules like:

```text
model favorite >= 60%
AND pick_elo_diff < 0
AND edge is thin
=> skip or require better price
```

#### 5. Underdog upgrades

Question:

```text
Are underdogs with ELO advantage profitable?
```

Tests:

- market underdog + positive ELO diff
- model pick underdog + positive ELO diff
- skipped underdogs with positive ELO diff
- underdog ROI by ELO bucket

What we are looking for:

- spots where market price lags strength-of-schedule or recent quality
- underdogs that should be upgraded into a watchlist or small-bet bucket

#### 6. ELO vs current betting rules

Question:

```text
Would ELO have improved our existing bet/skip rules?
```

Tests:

- current bets filtered by ELO agreement
- current skipped fights that ELO would upgrade
- current bets that ELO would downgrade
- ROI by `skip_reason` and ELO bucket

What we are looking for:

- whether ELO is additive to the current thresholds
- whether ELO catches specific skip-rule blind spots

#### 7. ELO derivatives

Question:

```text
Is the useful signal in raw ELO, ELO direction, or derived ELO context?
```

Candidate derived fields:

- `pick_elo_diff`
- `abs_elo_diff`
- `pick_has_elo_advantage`
- `model_agrees_with_elo`
- `market_agrees_with_elo`
- `model_market_elo_triangle`
- `elo_edge`: model probability minus ELO-implied probability
- `elo_market_gap`: market implied probability minus ELO-implied probability

Future derivative fields after Phase 2:

- recent ELO momentum
- current vs peak ELO decline
- average prior opponent ELO
- recent opponent quality
- best win ELO
- loss quality

```text

```

Example:

```bash

```

It consumes `v_agent_packet_evidence`, groups evidence into support/caution/context/audit sections, and cites `evidence_id` values (for example `[E4861]`). Default mode is deterministic. `--llm` adds an evidence-only reasoning layer on top of the deterministic scaffold and validates that every generated claim cites known `evidence_id` values from the packet. It still does not output a bet/skip recommendation.

Packets also include `pattern_score_v0`, which is intentionally data-derived from aggregate pattern stats rather than hand-weighted:

```text
strong:   N>=50, win_rate>=70%, ROI>=15% => score 8
moderate: N>=30, win_rate>=65%, ROI>=5%  => score 7
mild:     N>=20, win_rate>=60%, ROI>0%   => score 6
negative: N>=20, ROI<=0%                 => score 4
```

`N` is always the graded historical sample size. Pending/current/future rows that match the pattern are reported separately as ungraded matches and do not affect win rate, ROI, or score.

When multiple applicable patterns qualify, the score should prefer the most specific decision-relevant pattern over broad base rates. For example, prefer `skip_50_65_elo_50_plus` over `model_pick_higher_elo` for a below-threshold skipped pick.

For auditability, `context_packet.py --expand-source-pattern` prints the exact rows behind the selected score source pattern. The expansion is graded-only by default; `--include-pending` adds current/future ungraded matches.

`backtest/context_candidates.py` is the batch watchlist layer. It scans pending skipped model picks, applies the same deterministic packet scoring, and ranks fights that merit deeper evidence review. It is not a rule change and does not place or recommend bets by itself.

`backtest/validate_context_pipeline.py` is the promotion gate for the independent context pipeline. It validates `pattern_score_v0` on historical graded fights, using leave-one-out evidence by default so a fight does not grade itself. It reports performance by score, source pattern, season, bet/skip status, edge bucket, and odds bucket before any app/UI/LLM integration.

```text
market: -180
edge: thin
context:
  - fragile favorite
  - poor anti-control score
  - high variance striking matchup
  - similar favorites underperformed
decision: skip / downgrade
```

#### Upgrade an underdog

```text
base model: 43%
market: +220
context:
  + elite cardio gap
  + opponent fades after round 1
  + underdog has offensive control path
  + similar matchups produced frequent upset/control wins
decision: watchlist or small bet if edge threshold met
```

### Acceptance criteria

- Every decision has reason codes.
- Every reason code is tied to measurable traits or retrieved examples.
- Backtest reports can compare:
  - current rigid rules
  - context-upgraded picks
  - context-downgraded skips
  - context score by ROI

## Phase 8 — Backtesting the contextual system

### Objective

Prove whether the context layer improves betting outcomes before it affects live decisions.

### Backtest design

Run on true out-of-sample fights first:

- 2025
- 2026

Compare:

1. current rules
2. current rules + ELO-only filters
3. current rules + trait risk flags
4. current rules + context upgrades/downgrades
5. relaxed confidence threshold + context score

### Key experiments

#### 51-60% confidence zone

This is the zone where context matters most.

Questions:

- Which 51-60% picks were profitable?
- Did ELO advantage separate good from bad thin edges?
- Did control/cardio/durability traits separate good from bad thin edges?
- Could context_score identify strong 51% bets?

#### Favorite downgrade zone

Questions:

- Which favorites over 60% failed?
- Were failed favorites more likely to have:
  - high durability risk
  - bad anti-control
  - poor cardio
  - weak opponent quality
  - high variance score?

#### Underdog upgrade zone

Questions:

- Which underdogs won despite low base probability?
- Were they more likely to have:
  - ELO/opponent-quality advantage
  - control path
  - cardio advantage
  - opponent durability risk?

### Metrics

- profit
- hit rate

- calibration by context bucket

- drawdown
- profit by odds bucket
- profit by trait reason code

### Acceptance criteria

- Context layer must improve either:
  - ROI at similar bet count
  - profit at acceptable ROI
  - drawdown/risk profile
  - calibration in key buckets
- If it does not improve results, keep it as explanation only.

## Phase 10 — LLM observation layer

### Objective

Use an LLM to summarize evidence, not invent it.

### Inputs to LLM

Only pass structured context:

- model probability
- odds/edge
- current deterministic bet/skip rule and skip reason
- ELO deltas and ELO-derived findings
- trait deltas
- risk/support flags
- similar matchup summaries
- historical ROI/hit-rate for matching patterns
- selected recent fight evidence
- Sergey qualitative labels when present
- missing data warnings and minimum-sample flags

### Output contract

The LLM should output JSON:

```json
{
  "summary": "...",
  "upgrade_case": ["..."],
  "downgrade_case": ["..."],
  "key_risks": ["..."],
  "confidence_modifier": "upgrade|hold|downgrade",
  "context_score": 8,
  "context_score_reason": "...",
  "final_action": "eligible_bet|lean|skip|downgrade|human_review",
  "evidence_ids": ["..."]
}
```

### LLM context review table

Store the LLM output separately from the deterministic packet.

```text
llm_context_reviews
```

Suggested columns:

```text
review_id
packet_id
model_name
prompt_version
context_score
confidence_modifier
final_action
summary
upgrade_case_json
downgrade_case_json
key_risks_json
evidence_ids_json
raw_response_json
created_at
```

The packet is the source of truth. The LLM review is an interpretation of that packet.

### Guardrails

- No unsupported claims.
- No "I watched tape" language.
- No new injury/news claims unless retrieved from an approved source.
- No betting recommendation unless the deterministic context engine allows it.
- No final action above `lean` if required evidence is missing.
- No `8/10` or higher score unless at least two independent support families agree, such as ELO + retrieval, control trait + retrieval, or cardio trait + historical pattern stats.
- Must cite evidence IDs for every upgrade/downgrade claim.

### Acceptance criteria

- LLM summary is reproducible enough for audit.
- Each claim maps to a trait, metric, or retrieved matchup.
- LLM can be disabled without breaking the decision engine.

## First recommended implementation sequence

## Definition of success

The dream version is working when the system can say:

```text
The model only gives this fighter 51%, but this is a bettable 51% because:

1. The fighter has a +118 pre-fight ELO edge.
2. Their recent opponent quality is materially stronger.
3. Their offensive control score is high while the opponent's anti-control score is weak.
4. Similar historical matchups went 16-8 with positive ROI.
5. No major durability or cardio risk is present.

Recommendation: eligible small bet, not because the model is more confident, but because the context supports the thin edge.
```

And it can also say:

```text
The model gives this favorite 66%, but this is a weak 66% because:

1. The favorite has high defensive exposure.
2. The opponent has early finishing upside.
3. The favorite's cardio drops late.
4. Similar high-variance favorites underperformed at this price.

Recommendation: skip or require a better line.
```

That is the target: **stats-driven tape review for bet/skip decisions.**
